## Registry meaning and maintenance rules

Read this section before interpreting, editing, migrating or exporting the Movement workbook's `ТВО` table. One row describes one person's admission or one interval of acting duties in a particular replaced position. It is not the absent person's absence record. The row's name, tax ID and rank belong to the acting person. The replaced position identifies whose duties that person performs; an optional explanation names the replaced person and the reason.

### Column contract

Actual headers are configured in PROD and TEST under `returnTvo.table.headers`. Do not rely on worksheet column letters or the currently selected cell.

| Worksheet column | Internal field | Meaning and write rule |
| --- | --- | --- |
| `Звання` | `PersonRank` | Rank of the acting person. |
| `ПІБ` | `PersonName` | Name of the acting person, not the absent person. |
| `ІПН` | `PersonId` | Tax ID of the acting person; use it to resolve their Personnel record. |
| `Посада.Своя` | `OwnPositionCode` | The acting person's own staff-position code from Personnel. It also leads to the next person in a nested replacement chain. |
| `Посада.Заміщує` | `PositionCode` | Code of the position being temporarily filled. A history child's `DutyPositionCode` contains its immediate parent's `PositionCode`; use that replaced post, never the acting person's own code. |
| `Термін` | `Duration` | Assignment category. Use `Інше` for absence-related temporary replacement, including hospital/treatment and any vacation. This is not a numeric count of absence days. See the category rule below. |
| `Доступ.Наказ` | `AccessOrder` | Order granting admission/access to the position. Admission alone does not prove that duties started. |
| `Прийняття.Наказ` | `StartOrder` | Order recording actual acceptance of duties. Together with `Прийняття`, starts an executing assignment. |
| `Прийняття` | `StartDate` | Actual acceptance date, inclusive. A supplied acceptance order without this date is an error. A date without an acceptance order does not establish execution. |
| `Здавання.План` | `PlannedEndDate` | Expected handover/return date. Planning information only; it never closes the assignment. For vacation, use the day after its inclusive last day. |
| `Здавання` | `EndDate` | Actual handover date. The assignment no longer applies on this date in ordinary date-based reporter lookup. |
| `Здавання.Наказ` | `EndOrder` | Order recording actual handover. It is separate from admission and acceptance orders. |
| `Прийняття.Підстава` | `StartBasis` | Documentary basis for starting this assignment segment. The exporter uses the departure-side basis. |
| `Здавання.Підстава` | `EndBasis` | Documentary basis for ending this assignment segment. The exporter uses the arrival/closing-side basis. |
| `Додаткова інформація` | `Information` | Explanation of whom the actor replaces and why the original person is absent. Generated by the TVO text template; in a chain, distinguish the immediate replaced person from the original absent person. |

Other workbook columns, such as `УІД` when present, are outside this export mapping. Preserve their existing formulas, values and formatting; do not invent values or replace them with a tax ID. Never overwrite formula cells just to complete the mapped fields.

### The `Інше` category

For a person temporarily replacing somebody who left for a hospital, treatment or vacation of any type, set `Термін = Інше`. The same category applies to successors within that absence-related replacement chain. Put the specific absence reason in `Додаткова інформація`, not in `Термін`. Current Movement templates use `Інше` for every new departure/status-transition TVO segment, including other configured absence reasons.

For example, an absence of `15` days or `15+4` road days does not produce `Термін = 15`, `19`, `4М` or `6М`. Existing categories such as `4М` and `6М` are not defined by this absence exporter: preserve them when reading existing records, do not reinterpret their meaning or bulk-convert them to `Інше` without a separate business rule. Actual assignment activity is determined by acceptance and handover fields, not by this category.

### How to interpret a row

- Admission only: `Доступ.Наказ` is filled, `Прийняття.Наказ` is empty. The person is admitted, but the row is not evidence that they execute duties. Do not fill acceptance fields or restore duties merely because an admission exists.
- Executing assignment: acceptance order and acceptance date are both present. On a requested date, the interval is active when `Прийняття <= date` and actual `Здавання` is empty or later than that date.
- Planned return: a filled `Здавання.План` alone changes neither activity nor the actual end. A passed planned date must not automatically close a row.
- Closed assignment: actual `Здавання` records handover; preserve its order and basis as part of the historical segment. A repeated arrival export may recognize that same date/order without creating a second handover.
- Status change: close the old accepted segment and open its successor on the transition date. Preserve the old segment even when the acting person stays the same; it documents a different absence reason or period.

Example: ВАРАВА Віталій Юрійович leaves his position `В00К3967` on annual vacation from 23 October 2026 for 15 days. ОНИЩЕНКО Сергій Олександрович replaces him, with own position `В00К3889`. The TVO row must name ОНИЩЕНКО, set `Посада.Своя = В00К3889`, `Посада.Заміщує = В00К3967`, and `Термін = Інше`. Its explanation states that he replaces ВАРАВА because of annual vacation. The last vacation day is 6 November; planned handover is 7 November. Actual handover fields remain empty until the corresponding return/transition is recorded.

In a chain where A leaves, B replaces A and C replaces B, B's row targets A's position and C's row targets B's position. Each row retains its actor's own position. Do not flatten both rows onto A's post or copy the original absent person's identity into either actor's fields.

### Rules for changes and reuse in other chats

Resolve the actor by `ІПН`, identify the replaced post separately, and inspect the relevant acceptance/handover interval before changing a row. Never assume that the last physical row or the first matching name is the current assignment. Overlapping executing assignments for the same post, cycles, missing identity/post data and incomplete accepted assignments require explicit correction rather than guesses. Re-export must not create duplicate accepted segments.

Use the dedicated `ТВО` registry for new assignments and closures. The absence table's `ТВО.ПІБ`, `ТВО.ІПН` and `ТВО.Посада` are a legacy read-only fallback for restoring old departures: do not write new assignments there or clear historical values as part of routine export. Dedicated registry records take precedence; an admission-only registry record must not be bypassed to promote someone through the legacy fallback.

Preserve row and column formatting and workbook formulas; write only mapped values. Preview uses loaded dependency snapshots, while persistence and actual export retain their separate validation rules. Reading an existing workbook, correcting its data, importing VBA and saving/exporting are distinct actions: a documentation or source-code task does not authorize changing the working registry.

## Export implementation

History TVO children retain their actor's own `PositionCode`. During history loading, `DutyPositionCode` and `DutyPersonName` come from the immediate parent, including nested replacements. The Movement planner copies these rows and uses `DutyPositionCode` as the replaced post without altering the stored child or its Word context. Existing registry and return rows already contain the replaced post. Assignment comparison uses the same normalized metadata as insertion.

New departure and transition segments render their text columns from `PersonalEventBuilderMovementTemplates.xml`. A `column` without `target`, or with `target="Absence"`, belongs to the absence table. A `column target="TVO"` belongs to the TVO table and is rendered once per assignment before planning the cell changes. `configKey` resolves the destination header through wsConfig; text content, conditions and reasons live in XML. Missing or invalid TVO templates stop the operation before writes. These fields participate in previews, conflict stamps, verification and rollback. Previously exported rows are not automatically repaired.

```xml
<column configKey="returnTvo.table.headers.Duration"
        target="TVO">
  <text>Інше</text>
</column>
<column configKey="returnTvo.table.headers.Information"
        target="TVO">
  <text>{#include block.TvoInformation}</text>
</column>
```

Each departure/transition template declares both columns. The shared `block.TvoInformation` uses `TvoReplacedPersonName` for the immediate replaced person, `PersonName` for the original absent person, and `TvoIsChain` to select the chain wording. The `TvoDepartureReasons` XML dictionary supplies the reason by `TargetStatus`. All other prepared Movement fields remain available. wsConfig retains only header mappings; `returnTvo.table.values` and `returnTvo.reasons` are no longer used.

An admission (`Доступ.Наказ`) is distinct from acceptance of duties. A row without `Прийняття.Наказ` is not an executing assignment, even when it has an admission order or a provisional date. Such a registry row restores no duties and suppresses legacy fallback for that represented position. Departure/transition metadata must not promote that admitted person into a new accepted segment or fill acceptance/handover fields. Accepted segments may still continue through transitions, and accepted assignments with a missing acceptance date remain errors. `MOVEMENT_TVO_EVENT`, `MOVEMENT_TVO_NOT_STARTED` and `MOVEMENT_TVO_ADMISSION_RETAINED` log the event context and admission decisions.

Movement export plans changes to both the configured absence ListObject and the `ТВО` ListObject in the same open target workbook. `returnTvo.table.name` and `returnTvo.table.headers` configure the TVO destination in PROD and TEST. The worksheet is shared with `reporter.tvo.source.sheet`. No source workbook is saved, opened or closed by the writer.

On arrival, return-duty restoration first follows assignments whose replaced position matches the returning person's absence-period position. Each actor's stored own position leads to the next replacement in the chain. The assignment must have started by the event date; an actual handover ends its interval. A handover already recorded on that event's date and order remains readable for repeat arrival previews. Assignments closed before the relevant absence period do not suppress legacy restoration. Cycles, overlapping active assignments and incomplete identity or position data stop processing.

When a corresponding TVO registry record exists, it takes priority over the old absence columns. Only an unrepresented absence falls back to `ТВО.ПІБ`, `ТВО.ІПН` and `ТВО.Посада`. Existing explicit history children and frozen return snapshots retain their established preview semantics. The Movement writer independently closes the applicable live registry chain, including when an older event snapshot contains different return-duty children.

Arrivals fill actual handover date, order and basis in the applicable TVO rows. Status transitions close the previous assignment segments and open successor segments; if the old period exists only in legacy columns, the new segment is created directly in the TVO table. Departures with duties create new assignment rows. New rows contain the actor's name, tax ID, rank and own personnel position, replaced position, acceptance/access order, acceptance date and basis, and an available planned end date. A planned end date does not close an assignment. New exports never write the three legacy absence columns.

The planner models the whole order before any writes. It validates destination headers, formulas, free expansion ranges and assignment overlaps. Already-applied events do not create duplicate TVO segments. Full table value/formula stamps detect changes between planning and writing; number formats do not participate in conflict or content verification. Actual TVO cell changes appear in the same pre-write diff as absence changes. Buttons above the diff select the absence or TVO worksheet using the actual configured worksheet names.

Arrival preview reads the prepared Movement and TVO snapshots, including the personnel index for absence rows. Requesting legacy TVO columns does not force a fresh read in preview. Saving an event retains the default fresh-source check before freezing its return snapshot; preview data alone is not treated as persistence validation.

The planned TVO handover date is the return day, one day after the inclusive vacation end (`DateToShort`). For example, departure on 23 October 2026 for 15 days gives the last vacation day of 6 November and planned handover on 7 November. Empty vacation end dates leave the planned handover empty.

The writer snapshots TVO cell values and formats and any blank extension area. It appends rows through `ListRows.Add(AlwaysInsert:=False)` and transfers formatting properties directly from the preceding table row, including fonts, number formats, alignment, fills and borders. Excel's automatic per-column inheritance can otherwise mix font sizes within the new row. This uses neither the clipboard nor `Copy/PasteSpecial`; existing values and formulas are not copied. Temporary text number formats are restored after each value write. TVO writes and verification occur before export journaling; failures restore both tables, their original dimensions and changed cell values/number formats. Restoration failures are reported. The writer does not save the target workbook.

Revisions that would rewrite an active TVO chain, and cancellation of a represented TVO assignment, are currently rejected for manual review rather than silently changing registry history. Automatic cancellation/revision reconciliation of existing TVO intervals requires a separate design for persistent event identity in this table.

Static checks: `validate_movement_tvo.py`, `validate_return_tvo.py`, `validate_movement_diff.py`, configuration/snapshot checks, VBA structure/size checks and UI style/XML checks. These checks do not execute Office or verify Excel runtime behavior. Runtime acceptance must cover a new departure, a transition continuing an assignment, a legacy-only transition, an arrival with a registry chain, a legacy-only arrival, repeated export, conflicting assignments and a forced failure after TVO writes to verify joint rollback.
