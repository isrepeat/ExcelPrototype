# EventsHistory validation and Movement export

## Save-time scope

The save gate deliberately implements only three rules: an arrival needs an open departure; the arrival's source type must match that departure; a departure needs the previous absence to be closed. A transition closes its source type and opens its target type. Dates and RowOrder establish sequence only; the save gate does not check date ranges, chronology constraints, overlap, source destination, target hashes, links or future-event compatibility. Full export remains responsible for its stronger checks.

The single native event registry is ex_PEB_MovementRegistry: operation is Departure, Arrival or Transition (status change), with sourceStatus and targetStatus referring to configured absence types. fn_TryEvent identifies supported Movement events without loading exporter text templates. fn_EventsByOperation returns a slice of registered event IDs for one operation. Full export uses the same registry; there is no second independently maintained arrival/departure map.

## Saving an event

ex_PEB_History.fn_Save builds the candidate and operation-local history indexes during its existing read, then calls ex_PEB_HistoryEvntVldtn.fn_Validate before writing rows or revisions. The gate reads only the current PersonId's latest snapshot period through ex_PEB_MovementSource.fn_ReadLatest. No snapshot or result is cached between calls, and there is no preparation command or artificial time limit.

The source reader selects three fields: EventName, DepartureDate and ArrivalDate. For a closed snapshot it uses a parameterized SELECT TOP 1 ordered by departure descending; an open period wins a departure-date tie. For an open workbook it reads the ID column and compares only that person's matching records using the same date/open-state preference. The configured source path, sheet, table and explicit closed-file range remain unchanged. No hidden Excel session is created, and no PEB ID/hash columns are needed by this reader. An absent period produces a closed/empty starting state.

The state contains only IsOpen and Type. It starts from the snapshot period; ArrivalDate is used only to distinguish an open period and establish its represented event date. EventsHistory roots for the current IPN are considered in EventDate/RowOrder order, excluding the previous version of the current RowId, cancelled roots and roots after the candidate. A type/date boundary identifies the snapshot state already represented in history so it is not applied twice. This is lightweight state reconciliation, not adoption of target links or proof of export eligibility. An edited or cancelled boundary is reversed only as an open/closed type state.

Active pending events after that boundary update the state using the same three rules, then the candidate is checked. Thus an arrival saved in EventsHistory can close an absence still open in the snapshot and allow a subsequent departure. An incompatible pending arrival cannot close it. Cancel requests themselves bypass the add-event checks and remain subject to the existing cancellation/export workflow.

This gate is intentionally a latest-state check, not a reconstruction of every historical period. It does not prove that backdated changes or later events remain exportable. Ordering requires readable date values, but no business date constraints are imposed. Full export retains its RowId/hash, date, period, formula, destination and manual-change protections.

The closed-file SQL range is validation.Movement.source.range (currently B6:AZ20000); it must cover the actual headers and data. ACE identifier normalization replaces dots with number signs, while open Excel lookups use the original headers. The reader closes its ADO connection each time. Movement.SaveValidation.ReadLatest/Rules/Total measure the source read and the small state check; EventsHistory IO and persistence are outside this timer.

## Exporting an order

ex_PEB_MovementBatch.fn_ExportOrder resolves exactly one configured open worksheet/table (currently TV on the configured absence sheet), validates its writability and asks ex_PEB_MovementPlanner.fn_BuildOrder for one plan. There are no closing-versus-other-operation writer branches, repeated rebuilds or verification through another export simulation.

The planner reads the order from EventsHistory, loads target rows for the selected people, sorts events by EventDate/RowOrder and prepares Movement column texts from saved scalar/child data. It never rereads lookup workbooks or prepares Word output. Unsupported additional reports remain explicit conflicts. Native append, close and transition routes remain available.

Shared state rules select the source period; the planner maps that selected model index to the physical target row. It also guards formulas, nonempty closing fields, unrelated historical same-day boundaries, duplicate or incomplete links and unsupported changes to applied data. Final periods are checked before writing. A conflicting event blocks the complete order.

The plan contains context, Actions, ConflictCount, IsReady, TargetStamp and PlanStamp. It does not retain the entire simulated table. TargetStamp describes table identity, location, dimensions, headers and totals. PlanStamp covers operations, event stamps, row indexes and mapped writes. Plans are built and immediately applied in the same synchronous call; a persisted or externally reviewed plan is not an execution API.

ex_PEB_MovementWriter.fn_Apply is the single writer for append, close, transition, basis correction and supported closing cancellation. It captures the affected cells and coalesces repeated writes to the same cell, requiring their expected intermediate values to agree. Adding rows captures only the empty extension area and its number formats. Existing TV rows are never snapshotted wholesale.

The four configured link columns must already exist. Append requires an empty, unmerged extension area that does not intersect another table; appending with a totals row is explicitly unsupported in this baseline. Expansion uses ListObject.Resize without inserting worksheet cells. On failure the writer restores changed cells, original table dimensions and extension contents/formats. It verifies written/restored fields directly instead of rebuilding the order.

Events, screen updates, calculation and automatic formula filling are suspended during mutation and restored on every exit. Calculation is restored before events/screen updates. The writer records successful application in ExportJournal and leaves the target workbook open and unsaved. No backup file, AutoSave manipulation or workbook.Saved requirement is introduced.

## Links and supported corrections

PEB.OpeningId/OpeningHash and PEB.ClosingId/ClosingHash independently link the two sides of a period. A transition uses its RowId on the source closing side and destination opening side. Older target rows may have empty opening links. Hashes remain H1- plus 16 hexadecimal characters over the relevant mapped fields; they are integrity checks, not cryptographic audit protection.

Re-export checks actual mapped fields against the stored hash before comparing new values. Unchanged events are skipped. Only basis-field corrections are supported for already applied events; the corresponding hash is updated with the basis. Other mapped changes require reconciliation. Manual target changes and ambiguous matches remain conflicts. Closing cancellation clears only its linked closing fields and is validated against later periods. Word and EventsHistory retain ticket fields; Movement basis templates omit current and previous leave tickets.

## Deployment and verification

Deploy the VBA profile, UI and both wsConfig files together. The new source and writer modules are ex_PEB_MovementSource and ex_PEB_MovementWriter. ex_PEB_MovementClose has been removed from the source profile; the preparation control, handlers, bindings and configuration keys have also been removed. No workbook data structure changes are required.

Movement.SaveValidation.ReadModel/Rules/Total and Movement.Export.TotalIncludingCalculation timings remain available. The writer also measures capture, write, verification, rollback and settings restoration. No artificial timeout is a speed guarantee. Initial targets (one-second save validation, 50-event export within ten seconds) require measurements in the actual Excel environment; source-only checks cannot establish them.

Static checks cover one plan/one writer, SQL parameterization and latest-period selection, absence of hidden Excel sessions and persistent validation state, registry consistency, the three save rules, revision/journal integration and rollback ordering. Runtime cases should include correct/incorrect return types, a pending arrival followed by a departure, a transition, basis updates, cancellation, manual target edits and a forced failure after table expansion. Record end-to-end save time separately because EventsHistory IO and workbook saving remain outside semantic validation.

## Revision storage

Deploy ex_PEB_HistoryRevisions, the changed history/controller/export modules, MainPage.xaml and both wsConfig profiles together. Create all sheets, tables and columns manually before using the new functions. The code never creates sheets, tables or columns; missing required structure stops the operation. Add Revision, Status and LastChangeId to tbEventsHistory, prepare EventRevisions/tbEventRevisions and ExportJournal/tbExportJournal. Legacy empty state cells read as revision 0 / Active without changing the workbook. Their first edit or explicit history view records a Baseline snapshot before the new version; earlier changes are unknown. Existing events are migrated lazily, not rewritten on a read.

EventRevisions / tbEventRevisions is an append-only application journal. Its first nine columns, in order, are ChangeId, EventRowId, Revision, ChangedAt, ChangedBy, ChangeType, Reason, ChangedFields and Status. After them, add one Snapshot.<header> column for each physical header mapped by history.fields (for example Snapshot.OrderNumber and Snapshot.PrevVacationTicketDate, rather than their internal alias names). Snapshot.Revision, Snapshot.Status and Snapshot.LastChangeId are not required. ExportJournal requires the eight columns configured by history.exports.fields in exactly that order. Format table data as text. Revision metadata and snapshot rows are appended by code to the prepared tables.

Each snapshot contains the event and its related Document, Report and nested TVO rows. Related rows share the change ID. Create, Update, Cancel and Restore create versions; an unchanged save does not. Status transitions require a reason. Snapshot rows and the current record are saved once in the same history workbook. On failure, appended snapshot rows and current values/formats are rolled back; rollback failures are reported.

The event list exposes Status, Revision, MovementSync and WordSync. Select an event and use EventVersions to open its journal filtered by EventRowId; this also establishes a baseline when needed. ChangedFields identifies edited scalar fields, and filtering two revision numbers exposes their full before/after snapshots. CancelEvent and RestoreEvent request a reason and save a new desired state. They do not immediately mutate Movement or Word. A new version is compared with the last successful journal record for each exporter; an unconfirmed cancellation is shown explicitly. Sync labels refer to the most recent target used by that exporter; ExportJournal retains its exact target.

ExportJournal / tbExportJournal records event ID, revision, application time/user, exporter, target, result and history stamp. Movement writes its journal after verifying target writes and before reporting success; a journal failure enters the target rollback path. Repeated no-op exports can record confirmation without changing Movement. Word records generated/omitted event versions after generating the output. A Word journal failure reports that the file exists but its audit record failed. Failed attempts also remain in the existing diagnostic log; the export table records successful applications/confirmations.

Cancelled events remain in history and the order list. Word regenerates from active events; cancelled versions are marked CancelledOmitted in a successful generation journal. If all events are cancelled, generation stops with an explicit message and leaves the previous Word file unchanged.

Cancellation of an applied close verifies its closing hash, joins and formula guards, clears only mapped closing fields and ClosingId/ClosingHash, then validates the affected person's complete modeled chain. An overlap caused by reopening the period blocks the complete package. Original opening fields and links remain unchanged. Cancellation with no target link is a no-op confirmation. Applied opening/transition cancellation is explicitly blocked in this stage; cancellation can remain pending while Word and Movement have different outcomes. Restore creates an Active revision; the normal exporter rechecks whether it can be applied.

History records edits made through the builder. Direct cell editing of EventsHistory, child rows or revision tables is not an audited editing API. User names are operational metadata, and editable Excel files are not a tamper-proof audit store. Date/person changes are versioned only when save-time validation accepts the candidate; changes to linked applied events still follow the supported basis-correction/closing-cancellation contract.

## Remaining export limits

The calculation model includes only people named in the selected order. Preview scans the PersonId column once and loads complete rows only for matching people, retaining physical SourceRow numbers for writes. Empty and single-row tables are handled explicitly. Technical link columns are checked globally for duplicate identities without creating unrelated row models. MOVEMENT_MODEL logs People, SelectedRows and TotalRows. There is no conservative full-table writer path.

Timings include Movement.Preview.ReadEvents, Movement.Preview.Model, Movement.Preview.Events and Movement.Write.Validate/Capture/Write/Verify/Rollback/RestoreSettings. Movement.Write.TotalIncludingCalculation and Movement.Export.TotalIncludingCalculation are recorded after restoring calculation, events and screen updating. RestoreSettings includes synchronous recalculation. These timers do not wait for unrelated asynchronous refresh work. No-op repeats skip writes and setting changes. Production-size performance remains unmeasured.

The preview combines Movement and the selected order only. Other unapplied orders are not merged. Old unlinked identity matches require an explicit migration/reconciliation workflow; automatic adoption is not implemented. Applied-event updates support basis text and closing cancellation. Changing dates, personnel, order fields or other exported fields, opening/transition cancellation and physical removal require a separate workflow; deleting an event from history does not remove its Movement record. If users delete both a target record and its links, these columns alone cannot prove that it had previously been applied. HistoryStamp is a comparison token, not a cryptographic hash or an independent ledger.

The module manifest selects the current PersonalEventBuilder sources, including Source, StateRules and Writer. The old single-event exporter remains for existing low-level test callers; the main ExportMovement command uses the batch path and refuses to run during an active legacy test session.

Static checks cover source limits, module conventions, configuration structure, route/template compatibility, batch safeguards and the absence of target writes in the planner. The exact parameterized three-field SELECT TOP 1/ORDER BY query was tested read-only through PowerShell/ACE against test_РУХ.xlsx. It returned the selected person's latest period without requiring PEB link columns or starting Excel. These checks did not execute VBA or measure production data. Full runtime correctness and export rollback still require explicitly authorized VBA scenarios on disposable workbooks. No such VBA execution is performed automatically.
