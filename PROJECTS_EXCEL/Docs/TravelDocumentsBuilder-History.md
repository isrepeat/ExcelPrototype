# TicketsHistory persistence

TravelDocumentsBuilder stores events in the open `TicketsHistory.xlsx` next to the application workbook. `history.path`, `history.sheet`, `history.table` and `history.versions` configure the target. The writer requires the exact configured workbook path, a writable workbook, and the configured column sets. It never opens, closes or saves the history workbook automatically. Deploy `ex_TDB_History`, the TDB generator, controller and page together with MainPage.xaml and wsConfig. The existing source profile includes the new module through `TravelDocumentsBuilder/*.vba`.

## Editing workflow

Load dependencies, select an order in the top UI block, then fill or load an event. The order picker uses the shared order resolver and loaded dependency snapshot, with nearby order suggestions and searches by number, date or number/date pair. The optional year disambiguates numbers and incomplete dates. Multiple matches are never accepted by choosing the first result; select the exact number/date pair. Then use Edit history to read all live events for that accepted order, independently of the person currently in the form. There is no all-orders or person-only history fallback. Save event writes only TicketsHistory; Export WORD regenerates the entire selected order from saved history. Unsaved form edits are not exported.

Confirm a history row with Ctrl+Enter to load its form, RowId, concurrency stamp and TVO chain. Selection checks the list's order scope and the selected record's captured event stamp, so a stale list cannot load a silently newer event. A visible indicator identifies editing mode. Entering editing mode temporarily disables personnel autofill, clearing the unrelated personnel selection. New event clears the editing identity and chain and restores the pre-edit autofill setting, retaining the accepted order. Closing the history table only hides it and does not discard the editing session. Accepting another order ends the old editing session. The same save button creates a new event or updates the loaded RowId, according to the current editing session. Both operations require the accepted order scope. Changes to the person's identity or event dates do not change that RowId or the existing ticket number. A separate duplicate check rejects another event with the same person, order number/date, vacation event and departure date.

## Autofill presentation and edit protection

The form uses the shared input control's readOnly binding and editor state tags, as PersonalEventBuilder does. With autofill enabled, populated rank, tax ID, own position code, position description, unit and TVO dependent fields are read-only. The accepted order is selected in the action block; the form has no duplicate order editor. These fields use PEB's personnel/current-order styles and muted read-only colors. Personnel and TVO name lookup keys remain editable. Disabling autofill unlocks the dependent fields for manual editing. Empty dependent fields are not locked. The field list and source-style names are configured under forms.readOnly and forms.sourceStyles; no new protection mechanism is added to the common engine.

The TVO controls select an actor from the personnel lookup. Add appends that actor to the end of the chain and clears the selection fields. Remove drops the last actor. To replace an intermediate actor, remove the suffix and rebuild it. A single selected actor can also be saved directly when the chain is empty. Pending actor fields beside an existing chain must be added or cleared explicitly.

## Current rows and revisions

Tickets uses the agreed 28-column English schema; TicketRevisions has nine metadata columns and 26 Snapshot columns. ReportNumber stores the report number, Basis stores only the basis text, and PositionName stores the position description separately from PositionCode. UI bindings ReportNo, Purpose and PersonUnit map to ReportNumber, Basis and UnitName. VacationKind and RowType replace the previous duplicated event description. Actual-return columns are not part of the schema.

Every current row has a GUID-based RowId. Event roots have no parent. Donation rows belong directly to the event. Each TVO row belongs to the immediately preceding actor or the event, retaining its own PositionCode and the immediate parent's code in DutyPositionCode. The reader rejects missing or duplicate IDs, unknown row types/statuses, missing parents, cycles, branching chains, duplicate actors/positions in a chain and invalid numeric revision values. These are event-specific replacement plans, not evidence of admission or actual acceptance/handover of duties in the Movement registry.

The event and its current children share Revision and Status. ChangeId is derived from the event RowId and Revision; Tickets has no LastChangeId column. TVO order is derived from ParentRowId links, without a RowOrder column. Each substantive change appends a complete snapshot to tbTicketRevisions: one row per event or child, grouped by `ChangeId = EventRowId/R<Revision>`. ChangeId repeats within a snapshot; the pair ChangeId and Snapshot.RowId must be unique. ChangedFields includes root fields and Children when any child content or membership changes. Create starts revision 1. Cancellation and restoration require a reason and preserve the event's identity. Removed children remain in older snapshots. There is no ExportJournal, ExportFieldState or ExportConflicts table.

An unchanged save does not add a revision. DocumentPath, DocumentRevision and DocumentGeneratedAt describe the latest generated document and do not themselves create business revisions. Saving a changed event leaves these fields describing the previous export until the next successful order export. Snapshot copies retain their values at the time a substantive revision was recorded; those three current document fields are excluded from snapshot integrity comparison. This is deliberately not a document export audit.

Loading and updating require a complete snapshot matching the current event graph. Unversioned or manually changed business rows are rejected rather than silently adopted. Restore them from the matching snapshot before editing. This implementation does not invent a migration baseline for legacy rows. The form's opaque stamp covers current event/child business fields, excludes the three export metadata fields and is never whitespace-normalized. Sorting the table does not change identity or the event stamp.

## Transaction boundaries

Saving captures the live history and revision tables and rechecks both fingerprints before writing. It updates the root and optional donation, synchronizes only that event's TVO rows and appends the revision. Failures restore both tables' contents and number formats and discard appended revisions. Both table restorations are attempted even if one fails, and restoration failures are reported. Saving does not require a Word template or output folder.

Order export uses `obj_TDB_OrderWordExport`, deployed with the other TDB sources. It reads verified saved event groups for the accepted order and freezes the template into a staging directory. One private Word session renders every Active root, including its donation and TVO chain. Rendering finishes before any existing document is replaced. Template, output-folder and both history-table fingerprints are checked before publication. Previous managed documents are backed up; the complete new set is published; then only current document metadata is updated. A failure removes newly published files, restores backups and rolls back metadata if necessary. Failed restoration retains the staging directory for recovery. These are in-session rollback guarantees, not crash-safe multi-file transactions.

Each order has a dedicated folder `TDB_<yyyyMMdd>_<order number>` beneath the configured output root. Managed filenames are `TDB_<ticket number>_<person name>__<RowId>.docx`; the GUID-based RowId is stable when the readable label changes. Synchronization replaces all managed files in that selected folder, adds new Active events and removes obsolete files, including Cancelled events. An empty active set removes the previous managed set. Strict filename markers identify ownership; previous RowId-prefix filenames are also managed and replaced on the next export, while unmarked documents are reported and left untouched. Other order folders are never scanned or removed. If events are moved between orders outside this UI, export both scopes to reconcile both folders. Changing the output root does not clean the previous root automatically.

All saved Tickets and TicketRevisions values are literal text with NumberFormat @, including dates, day counts and revision numbers. Dates use dd.mm.yyyy and are parsed explicitly without Windows locale assumptions. Legacy numeric date values remain readable and are converted to text when their event is saved. PlannedReturnDate is calculated in VBA as departure plus vacation, road and donation days, without an extra day; the form uses the same calculation and Word uses the saved date after checking it against the event durations. No worksheet formulas are created. Rollback captures values, original formats and actual formulas separately so literal text beginning with an equals sign is restored as text. Save TicketsHistory manually after saving events or exporting documents.

## Worksheet protection

The first history access protects Tickets and TicketRevisions with the `SHEET_PASSWORD` constant in `obj_TDB_HistoryProtection` (`TDB.Password`). All worksheet cells are locked; selection, copying and existing filters remain available. This is worksheet editing protection, not encryption or access control. The password is stored only in code. Save TicketsHistory manually to persist the initial protection.

`obj_TDB_HistoryProtection` owns both sheet references and uses the same password constant for protection and unprotection. Saving and Word-export metadata updates temporarily unprotect the sheets while events are disabled. A save restores protection before writing the recovery COMMIT marker. Any failure attempts to unlock for rollback and then protects both sheets independently, even if unlocking, rollback or the first sheet's protection failed. Protection errors are surfaced and logged; Dispose makes an additional best-effort attempt. Excel termination or interruption with VBA End cannot execute cleanup and is outside these guarantees. No UserInterfaceOnly session exemption is used.

## Recovery log

Substantive event saves append UTF-16 XML records to `TicketsHistory.xlsx.recovery.xml.log` beside the history workbook, using the same record format as PEB. PREPARE contains the previous and resulting event graphs, including donation/TVO children, and all newly appended revision rows. COMMIT confirms that the save was accepted. Recovery records are written after the in-memory revision is prepared and before the save is acknowledged; a journal write failure rolls back both tables. A PREPARE without COMMIT is incomplete and must not be treated as a successful save. Unchanged saves and Word-only exports do not append records. The log does not save the XLSX or restore it automatically and is separate from ExportJournal.

## Validation checks

Word export logs `TDB.Word.Export.Total` including Word shutdown, plus Prepare, RenderAll, Verify, PublishFiles, MetadataAndProtection, SessionClose and Cleanup timings. Per-document timings include Prepare, Create, ReplaceMarkers, Save, Close and Total, correlated by the event RowId/revision in Operation. Failures include the active stage and partial document total. Diagnostics are batched for the export. One hidden Word session opens DOCX files with Documents.Open (ReadOnly=True, Visible=False) and ScreenUpdating disabled. The frozen input is indexed once using Find.Execute, and every occurrence is saved as a uniquely named bookmark in a short-lived a.docx staging template. Later tickets open that indexed copy and replace bookmark ranges directly, without repeated marker searches. Linked stories are deduplicated by the generated bookmark prefix. Template.IndexMarkers and Template.SaveAnchors timings isolate the one-time cost. Documents.Add is not used for this DOCX input because it failed with Word error 5981. Excel events and screen updates remain disabled throughout rendering and Word shutdown; the original Excel window/sheet are restored before screen updates resume. The 30-documents-in-10-seconds target requires an authorized runtime measurement; static validation does not establish throughput.

Run `PROJECTS_EXCEL/WorkbookUpdater/Test-TravelDocumentsSources.py` and `Scripts/PowerShell/Test-UiStyleSources.ps1` for static configuration, actual XLSX schema, source boundary, filename ownership and markup checks. They do not compile or execute VBA. Runtime acceptance remains a separate authorized step: create/load/update, unchanged saves, changed identity with stable RowId, cancellation/restoration, multi-level TVO, donation removal, sorting, stale/manual edits, protected targets, missing DOCX, mixed managed/unmanaged files, zero-active export and forced rendering/publication/revision failures.
